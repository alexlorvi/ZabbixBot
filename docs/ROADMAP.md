# ZabbixBot — ідеї та плани

Тут зібрано функціонал, який ще не реалізовано, і план інтеграції зі script-server. Поточні технічні борги та
відомі недоліки коду — у [CLAUDE.md](../CLAUDE.md), розділ «Current state / open backlog».

Пріоритет: **P1** — найбільша користь за найменших зусиль, **P2** — корисно, **P3** — коли буде час.

## Функціонал

### P1. Квитування проблем з Telegram
- Відповідь (reply) на сповіщення про проблему → коментар у Zabbix (`event.acknowledge`, action = add message).
- Кнопки під сповіщенням і під `/ev<id>`: «✅ Квитувати», «💬 Коментар».
- Виконується **особистим токеном** користувача (`UserTokens`), тому діють його права в Zabbix і в історії
  видно, хто саме квитував.
- Що потрібно: зворотний пошук `message_id → event_id` в `AlertStore` (зараз файл іменується `<eventId>_<chatId>`);
  обробка `message.reply_to_message` у `BotController::handleWebhook()`; оновлення сповіщення у відповідь
  (Zabbix сам надішле update-повідомлення відповіддю на проблему — це вже працює).

### P1. Тимчасово вимкнути сповіщення (mute)
- Кнопки «🔕 1 год / 4 год / до ранку» в `/settings` і/або під сповіщенням.
- Варіанти реалізації: тимчасово обнулити severity-маску media (вже вміємо — `updateUserMediaSeverity()`) і
  повернути її cron-командою після закінчення; або Zabbix maintenance на хост (потребує ширших прав).
- Зберігати попередню маску й час закінчення в `User` (preferences), відновлення — `app:unmute` у cron.

### P2. Ранковий дайджест
- `app:digest` у cron: кожному користувачеві (або тим, хто ввімкнув у `/settings`) — підсумок відкритих проблем
  за групами/критичністю, кількість нових за ніч. Використовує вже наявні `getUserProblems()` + `EventFormatter`.

### P2. Ескалація неквитованих аварій
- Якщо проблема рівня Disaster (налаштовується) не квитована за N хвилин — повторне сповіщення або сповіщення
  в груповий чат чергової зміни. Частково можна зробити штатними escalation-кроками Zabbix; бот додає лише
  груповий чат як отримувача.

### P2. Розширена картка хоста (`/host`)
- Кнопки «📈 Графік» (зображення `chart2.php` / `chart.php` з Zabbix, надсилається як фото),
  «Останні дані» (ключові item-и: ping, loss, uptime), «Події за 24 год» (включно із закритими).

### P2. `app:uphost` — чекати на хост
- `/uphost <host> [хвилин]`: бот пінгує хост у фоні (cron/CLI) і повідомляє, коли він піднявся або
  коли сплив таймаут. Перевірка хоста — через `PingService::validHost()`.

### P3. Обрані команди
- Користувач зберігає часті запити (`/host Київ-01`, `/events Zabbix full`) як кнопки в `/menu`.
  Зберігання — `app/Models/User.php` (масив у preferences), керування — підменю в `/settings`.

### P3. Автовидалення сповіщень
- Telegram дозволяє боту видаляти повідомлення не старші за **48 годин**, тож реалістичний варіант —
  «видаляти пару проблема + відновлення через N годин після відновлення» (N < 48).
- `AlertStore` зараз видаляє запис при відновленні; для цього треба зберігати обидва `message_id` до дедлайну
  і чистити їх cron-командою.

### P3. Дрібниці
- Reply-клавіатура `/menu` після зміни мови: кнопки, надіслані старою мовою, не розпізнаються, поки
  користувач не відкриє `/menu` ще раз (можна розпізнавати підписи всіх мов).
- Пошук `/host` за тегом інвентаря (`inventory.tag`, як у TOP200).

## Інтеграція зі script-server

[bugy/script-server](https://github.com/bugy/script-server) — веб-інтерфейс для запуску скриптів.
У нас розгорнутий з **LDAP-авторизацією**.

### Що дає API script-server
| Дія | Endpoint |
|---|---|
| Список доступних скриптів | `GET /scripts` |
| Опис скрипта (параметри) | WebSocket `/scripts/{name}` |
| Запуск | `POST /executions/start` (multipart: назва скрипта + параметри), відповідь — id запуску |
| Стан | `GET /executions/status/{id}` |
| Вивід | WebSocket `/executions/io/{id}` або історія `GET /history/execution_log/long/{id}` |
| Зупинка | `POST /executions/stop/{id}` |
| Вхід | `POST /login` (форма username/password), далі cookie сесії + `X-Requested-With`/XSRF |

API-токенів немає. Ідентифікація заголовком (`access.user_header_name` + `access.trusted_ips`) працює **лише з
вимкненою авторизацією**. Точні імена полів форми запуску треба звірити з версією, що стоїть у нас.

### Варіанти

**А. Сервісний LDAP-акаунт бота (рекомендовано для старту)**
- Бот логіниться в script-server окремим LDAP-акаунтом, cookie сесії кешується (`FileCache`) і
  поновлюється при 401.
- Хто що може запускати, вирішує бот: у конфізі — відповідність «група Zabbix → дозволені скрипти»
  (членство в групах уже є в кеші `ZabbixService::telegramUsers()`, як для `isAdmin()`).
- Аудит: ініціатор (логін Zabbix + chat id) пишеться в лог бота і, якщо скрипт це підтримує, передається
  параметром.
- Мінус: у журналі script-server усі запуски — від імені сервісного акаунта.

**Б. Окремий екземпляр script-server без авторизації, лише для бота**
- Слухає тільки внутрішній інтерфейс, `trusted_ips` = хост бота, користувач — заголовком
  `user_header_name` = логін Zabbix.
- Плюс: працюють штатні `allowed_users`/групи script-server і його журнал показує реального користувача.
- Умова: логіни Zabbix збігаються з LDAP-логінами. Мінус: ще один сервіс для підтримки.

**В. Вводити LDAP-пароль у Telegram** — відхилено: паролі в історії чату.

### Як це виглядатиме в боті (варіант А)
1. `ScriptServerClient` (сервіс): login, `listScripts()`, `start($name, $params)`, `status($id)`, `output($id)`.
2. Конфіг `scriptserver`: `url`, `username`, `password`, `scripts` (назва → групи Zabbix, опис, параметри),
   `timeout`.
3. Команда `/run` — inline-список дозволених скриптів → запит параметрів (по одному повідомленню або
   кнопками для параметрів-списків) → підтвердження → запуск.
4. Результат: для коротких скриптів — чекати й надіслати вивід (`MessageService::sendMessage`, з розбиттям на
   частини); для довгих — повідомлення «запущено #id», а cron `app:script-status` надсилає результат після
   завершення.
5. Можливо: кнопка запуску скрипта прямо з картки хоста (`/host`) з підставленим IP.

### Що треба уточнити перед реалізацією
1. Версія script-server.
2. Які скрипти й з якими параметрами мають бути доступні з бота і кому (групи Zabbix?).
3. Чи збігаються логіни Zabbix і LDAP (критично для варіанту Б).
4. Чекати результат у чаті чи сповіщати після завершення; типова тривалість скриптів і розмір виводу.
5. Чи можна завести окремий LDAP-акаунт для бота.
